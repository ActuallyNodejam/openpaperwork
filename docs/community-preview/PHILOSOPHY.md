# Good work should not require becoming an AI expert

A person has a task, some files, a deadline and a standard they care about.
The product should meet them there. They should not need to understand models,
tool protocols or prompt engineering to get a useful result.

## Code and the model

Code does every step with a right answer; the model reads the mess, writes the words and picks. A script copies the figures, draws the page and runs the check. The model reads the person's own files, decides what the file should say, and fixes what the check names. Neither does the other's half.

## Put the complexity underneath

Chat is the ordinary way to ask, revise and finish. Controls can remain
available where they help, but the person should not need to configure the
agent before doing their work. Contributor-facing technical detail belongs in
development documentation, not in the language of the everyday task.

## The same standard from any agent

The library carries the rules and the check, so the person keeps the agent and
the model they already use. An invoice made in Claude and one made in
ChatGPT meet the same rules and pass the same check. Nobody should need a
particular model to get a correct file. When a file fails, fix the library or
the check, so every agent gains from it.

## Make what we can check explicit

A brief can require the right owners and dates. A spreadsheet can require
correct formulas and units. A deck can require readable text and an honest
chart. These requirements make parts of open-ended work testable.

Taste and judgment still matter. Mechanical checks establish facts about a
file; reviewers assess whether it communicates well and serves its purpose.
Neither should silently stand in for the other. A beautiful wrong answer
fails. A correct unreadable answer needs revision.

The reasoning and the limits are in
[Why standards](STANDARDS.md). To contribute one, see
[Add a standard](ADD_A_STANDARD.md).

## Learn from ordinary work

A small task can cross several files. A specialist task can be deep within
one document. Breadth and depth are separate dimensions, not a ranking of
industries or people. Start with general tasks and add domain packs only when
their sources, requirements and review expertise are clear.

When adding a national or institutional document requirement, record the exact
source, version and scope. A university submission guide is not a universal
rule for its country. Reusable production templates and the cases' expected answers
remain separate, linked by version.

## A bridge for contributors

Technical fluency can hide friction. Watch what a person has to understand,
repeat, set up or repair. Turn that observation into an example and an outcome
check. Improvements to examples, accessibility, translations, file quality and
cost reporting matter alongside code.

This is the direction we build toward. The cases and their checks show what
each pack covers today.
